# Teamroom 需求清单

## 产品目标与使用者

个人开发者在一个本地桌面工作群里管理多个 Agent 工具。用户是老板；每位员工有带产品名牌的原创卡通形象。用户通过 @ 明确交代工作，工具在群里报告进展、交付成果和提出审批；用户能查看每日工作与账户可用情况。

## 已确认的交互约束

- 首页采用工作群，不再提供独立「安排工作」表单。
- 输入 @ 弹出成员选择；点击群成员也能插入提及。
- 一条消息可包含多位员工；仅被 @ 的工具接收，重复提及去重。
- 无接收人、未知工具、空任务或任一接收人不可用时，整条发送失败并保留草稿。
- 每位员工展示产品名：Claude Code、Codex、OpenCode、Cursor、Cline、WorkBuddy。
- 日报先讲交付，再讲阻塞和下一步；每项成果可追溯到任务及执行记录。
- 演示状态、工具声明完成、老板验收、验证通过四种证据不得混用。

## 当前不做

自动拆分并自主选工具、自动充值、绕过登录或审批、抓取密码、强行控制桌面 GUI、团队云同步、无人值守修改共享目录、自动将未完成任务重新执行。

## 状态语义

排队 → 执行 → 等待审批 → 执行 → 待验收 → 已验收。失败、取消和中断各自保留。无事件只显示最近活动时间，不推断卡死；没有明确步骤清单，不生成完成百分比。

## 数据与账户

所有执行事件以 Task 为粒度；一个群消息可以产生多个任务。账户额度属于提供方账户，不属于卡通员工。多工具共用账户时不能重复累计余额或额度。历史导入必须标明覆盖范围，不能把缺失数据当作没有工作。
