# Teamroom 需求清单

## 产品目标与使用者

个人开发者在一个本地桌面工作群里管理多个 Agent 工具。用户是老板；每位员工有带产品名牌的原创卡通形象。用户通过 @ 明确交代工作，工具在群里报告进展、交付成果和提出审批；用户能查看每日工作与账户可用情况。

## 已确认的交互约束

- 首页采用工作群，不再提供独立「安排工作」表单。
- 输入 @ 弹出成员选择；点击群成员也能插入提及。
- 一条消息可包含多位员工；仅被 @ 的工具接收，重复提及去重。显式 `@all` 只广播给当前可用员工，不是隐式广播。
- 无接收人、未知工具、空任务或任一接收人不可用时，整条发送失败并保留草稿。
- 每位员工展示产品名：Claude Code、Codex、OpenCode、Cursor、Cline、WorkBuddy、Grok（实验性）。
- 日报先讲交付，再讲阻塞和下一步；每项成果可追溯到任务及执行记录。
- 演示状态、工具声明完成、老板验收、验证通过四种证据不得混用。

## 当前不做

自动拆分并自主选工具、自动充值、绕过登录或审批、抓取密码、强行控制桌面 GUI、团队云同步、无人值守修改共享目录、自动将未完成任务重新执行。

## 状态语义

排队 → 执行 → 等待审批 → 执行 → 待验收 → 已验收。失败、取消和中断各自保留。无事件只显示最近活动时间，不推断卡死；没有明确步骤清单，不生成完成百分比。

## 数据与账户

所有执行事件以 Task 为粒度；一个群消息可以产生多个任务。账户额度属于提供方账户，不属于卡通员工。多工具共用账户时不能重复累计余额或额度。历史导入必须标明覆盖范围，不能把缺失数据当作没有工作。

## 2026-10-17 新增确认

- 汇报节奏：工作中每 30 分钟有变化才汇报，每天北京时间 18:00 日报；完成、失败、审批即时提醒。
- Agent 在当前工具轮次安全结束后，用结构化请求提出不确定问题。暂停原任务，在群里邀请最多两名可用员工讨论；不会从自然语言猜测并自动重派。
- 讨论最多三轮，每轮包含员工回复与建议总结。共识不是测试通过，不能替老板批准权限或决策。
- 只有 Teamroom 发起并记录的工作进入自动统计；没有其他可用真实员工时明确等老板决定，不用演示数据冒充。
- Grok 是 2026-10-17 加入的实验性员工，使用独立 stdio JSON-RPC 适配器；现有证据只到协议夹具，真实 CLI、登录和模型可用性尚未验证，不能计入 v0.1 受支持适配器。
- `@all` 是老板显式选择全体当前可用员工，不是隐式广播；显式 @ 到不可用员工时仍按原有规则整条失败，不部分派发。
- Grok 使用 CSS 字标占位形象，未加入六宫格图集，不冒充已生成的官方吉祥物。
